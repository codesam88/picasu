# Test Strategy

## Goals

1. Catch each defect class at the earliest stage that can observe it. The layers below are ordered so that cheap, fast checks run first and expensive, broad checks run last — but every layer exists because some class of defect passes through all the layers above it.
2. Make important properties machine-checked, not review-checked. Checks that fail the build constrain every contribution including LLM-assisted ones; review discipline, human or otherwise, drifts. Where the behavior space is large, prefer derived and generated checks over hand-written examples.
3. Count only what is enforced. A property counts as covered only if a gate checks it on every change — or a stated advisory process triages it. Live status lives in `docs/quality-gates.md` (autogenerated from the justfile and workflows, self-checked); this document states intent, not status.

## Principles

1. Prefer getting it right by construction over checking it afterwards, and deterministic checks over review — human or machine. Generate or derive correctness where possible, and test only what construction cannot cover:

   - **Test** pure functions with non-trivial branches, schema contracts at boundaries where silent corruption is possible, integration paths where components interact in ways types don't constrain.
   - **Don't test** what the framework already guarantees: Rocket routing, redb read/write primitives, bitcode round-trips on unchanged structs, Vue rendering internals.

2. Derive checkable artifacts from the code, make them reviewable, impose them back as gates, and refine them from findings. The artifact in the middle is what reviewers read — the OpenAPI reference, the auth matrix, a Quint run trace — and it is generated, not hand-maintained, so it cannot silently diverge from the code it describes. The gate closes the loop in the other direction: openapi-sanity rejects annotations the handlers don't honor, dylint rejects code the annotations don't cover, the simulator's counterexamples become regression tests. A finding must change an artifact or a test; anything less is not a finding.

3. Do not trust a spec on authorship, human, macro, or model-generated. A hand-written spec goes stale when the code moves on; a macro-generated spec is only as current as its last run; an LLM-written spec may never have been true. The common case is the same in all three: the text exists, the code moved, nobody noticed. So treat every spec as untrusted input until a gate checks it and a refinement loop corrects it. This is what makes the Quint spec in this repo viable at all: it was read off the implementation rather than designed up front, which is fine, because nothing about it is taken on faith.

4. Verification must be deterministic and independent of what it checks. Generation is free — human, macro, or model-written — because its output is never trusted; a check earns trust only if its verdict depends solely on its inputs and it cannot fail the same way as the thing it checks. In practice: typecheckers, model checkers, property tests, diff gates against committed artifacts, selftests with deliberately wrong assertions that must fail, and independent derivations of the same property that must agree — the auth matrix against the probes, the Quint runs against the stateful tests.

5. Test behavior and implementation health separately. Passing workflow tests does not prove that public contracts are documented, architectural boundaries are preserved, or complexity and duplication have not grown. Those properties need their own executable checks and explicit budgets.

6. Assume drift; design for fast, loose change, by humans and by models. Review cannot keep up with that pace, and review discipline drifts even without it — so enforcement must not depend on anyone looking. That is why everything runs locally and the same gates run in CI: feedback in seconds, enforcement on every change, no human deciding whether this change needs checking.

## Overall pipeline

| Layer            | What it catches                                     | How                                                 | Gate                                                                   |
| ---------------- | --------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| Static (compile) | Category errors, unsafe code, style violations      | TypeScript, clippy, ESLint, `cargo fmt`/`prettier`  | gating                                                                 |
| Unit             | Pure-function logic errors                          | `#[cfg(test)]` blocks via `cargo test`              | gating                                                                 |
| Integration      | Multi-component interaction bugs                    | `src/tests/` against real redb in a tempdir         | gating                                                                 |
| E2E — API        | HTTP contract violations, regressions               | YAML scenarios → Rocket `local::Client`             | gating                                                                 |
| E2E — UI         | Full-stack user-flow regressions                    | YAML scenarios → Playwright                         | gating                                                                 |
| Contract         | Public API drift and compatibility errors           | OpenAPI generation, parity, lint, diff, smoke tests | gating                                                                 |
| Formal model     | Protocol errors on finite bounds                    | Quint spec + `quint test`                           | gating (Node-only runs; simulator advisory; Apalache/TLC out of scope) |
| Property/state   | Invariant and sequence errors                       | Property-based and model-based tests                | gating (in backend suite)                                              |
| Mutation         | Tests that pass despite meaningful behavior changes | Targeted mutation testing                           | planned                                                                |
| Architecture     | Dependency violations, churn, and code smells       | Boundary rules, quality budgets, artifact scans     | partial (`gates-check` wires recipes to CI; budgets planned)           |
| Precommit        | Format/lint plus branch-configured checks           | `just precommit`                                    | gating                                                                 |
| CI               | Current suite, audit, and release-build checks      | GitHub Actions                                      | gating                                                                 |

Each layer filters defects the previous ones cannot catch. Static analysis cannot verify multi-step index → dedup → flush → album update; integration tests can. Integration tests cannot verify HTTP response shape after a config change; API E2E can. API E2E cannot verify that a rescan converges the row after a filesystem change; the formal model plus stateful tests can.

Two build configurations: **developer** (debug, no `embed-frontend`, fast iteration) and **production** (release, `embed-frontend`, self-contained binary). `just precommit` runs the developer configuration. CI runs both to catch configuration-specific divergence before a release.

Live status — which gate runs in which lane — is `docs/quality-gates.md`, generated from the justfile and checked against it in CI. The table above states intent (`gating` means a gate exists and runs; `advisory` means run and triaged, never a gate; `planned` means designed but not built).

## Three approaches

Assurance effort prioritizes user authentication first, backend API assurance second, configuration and other functional domains third. The index pipeline work followed the same shape after them. Each domain reuses the same enforcement shape — analysis derived from definitions, tests derived from contracts, drift killed by parity gates — rather than inventing its own.

### Declarative scenario-driven testing (unit + e2e)

The oldest and broadest ladder: behavior declared in YAML given/when/assert files, executed against the real stack. `Given` materialises state through fixtures — interface adapters that translate abstract declarations into HTTP calls and filesystem operations, so when the backend's public API changes, only the fixtures change while the interpreter and the scenarios stay untouched. `When` dispatches HTTP calls (`local::Client`) or Playwright page actions. `Assert` checks responses, JSON bodies (dot-path navigation, counts, array predicates), filesystem state, and served images.

Two properties make this more than example tests. First, **selftests**: scenarios with deliberately wrong assertions that _must_ panic — a selftest that passes is a failure, so the assertion machinery itself is under test. Second, **negative tests**: generated wrong-credential, wrong-role, and wrong-principal cases assert the refusal paths, not just the happy paths. Drift resistance comes from the indirection: declarations stay stable while code moves underneath them.

Locations and runners: `backend/tests/scenarios/*.yaml` driven by `build.rs`-generated tests (`just backend-test`, one process per test); `frontend/tests/playwright/scenarios/*.yaml` driven by a Zod-validated loader (`just frontend-playwright`, against a built `dist/`, never the Vite dev server). AI-readable JSON reports support course-correction during development.

### Contract-derived assurance (`docs/api-assurance.md`)

The OpenAPI document plus the `x-picasu-auth` extension is the contract; correspondence rules (S1–S12) state each claim, what checks it, and whether it gates. Generators derive tests and fuzzing configuration from the contract (Schemathesis suites, generated negatives, auth matrix), so the handwritten suites pin flows while derived suites cover the cross-product. See the api-assurance doc for the full strategy, including its limits section — the honest-boundary convention this document follows.

### Formal models with enforced contracts (`docs/quint-modeling.md`)

Quint specs model one subsystem protocol at a time on finite bounds. Invariants state what must hold; the simulator explores interleavings and every violating trace becomes a regression test or a classified transient. Contracts are enforced where their inputs live: typestate and constructor-checked bundles at compile time, proptest properties for decision logic, stateful tests against the real backend for convergence. See [Quint Modeling](quint-modeling.md).

## How the two derived approaches map

Same pattern, two instantiations — contract-derived assurance and formal models answer the same questions with different sources of truth:

| Concern                            | API contracts (`docs/api-assurance.md`)                                                         | Index pipeline (`docs/quint-modeling.md`)                                                                                                                                 |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source of truth                    | OpenAPI + `x-picasu-auth` extension, generated from annotations                                 | Quint spec, written against the implementation                                                                                                                            |
| Human review surface               | auth matrix, OpenAPI reference, oasdiff diffs                                                   | The spec file itself plus simulator traces and `quint test` runs                                                                                                          |
| Derived contracts                  | S1–S12 table (Rule, Claim, Enforced by, Status)                                                 | `requirements.json` (goal-derived, owner plus gate) and generated `traceability.json`; simulator counterexamples become regression tests                                  |
| Imposed back on the implementation | `openapi-sanity`, dylint, Schemathesis suites                                                   | Typestate bundles, proptest properties, stateful sequences                                                                                                                |
| Living with the code               | Sandwich: annotations generate the spec that reviewers read                                     | Same requirement, different source: separately authored specs (by hand or derived with tooling) live beside the code and stay honest through gated, generated enforcement |
| Advisory tier                      | `fuzz-run` (time-budgeted, triaged, never gating)                                               | Quint simulator (same discipline)                                                                                                                                         |
| Coverage accounting                | Registry schema proposed, single schema intended for both approaches (no enforced registry yet) | `requirements.json` statuses plus the generated `traceability.json` closed-world audit                                                                                    |

Shared discipline, stated once: each rule lives where its inputs live; a found trace becomes a test or a classified exception with a reason, never a shrugged-off log line; prefer typestate and constructor-checked bundles, and reach for a lint only where types cannot express the rule; driver harnesses (serial lock, sync points, in-test model) are copied, not reinvented, across domains.

## Other notes

### What is not tested and why

| Area                                              | Reason                                                                                   |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Rocket route definitions                          | Framework handles dispatch; type-checked at compile time                                 |
| redb read/write primitives                        | Covered by redb's own test suite                                                         |
| bitcode round-trips on unchanged structs          | Covered by bitcode's own test suite; only the _version dispatch logic_ needs testing     |
| Vue component rendering                           | Deferred to E2E; unit-testing rendering adds maintenance cost without proportional value |
| Individual Pinia getters backed by a single field | No logic to test; the type system covers it                                              |

### Tooling caveats

- **`PICASU_WEAK_PWHASH`**: test-only argon2id cost override. Set to exactly `1` to run argon2id at trivial cost (m=8192 KiB, t=1, p=1) for both user and share password hashing; unset or any other value keeps production params (m=19456 KiB, t=2, p=1). Wired into `just backend-test` and the e2e backend launcher. The override is env-only and read per hash call, so tests can flip it within one process; never set in production.
- **clippy `unwrap_used`**: enforced under `-D warnings` over `--all-targets`, so test code is gated the same as lib and bins.
- **pinned toolchain**: `rust-toolchain.toml` pins the exact stable release (with `clippy` and `rustfmt` components) so dev machines and CI can never drift apart — a new upstream lint cannot break the gate by surprise. Dependabot's `rust-toolchain` updates propose the bump as a reviewable PR; CI stays green on the pin until it merges.
- **`cargo deny check`**: license and advisory audit, runs via `just audit`.
- **`npm audit`**: runs in CI on every PR, not in precommit (too slow, some findings intentional via `overrides`).
- **`npx knip`**: periodic dead-code sweep for the frontend; unsuitable for precommit.
