# MIRAI reachability PoC

Evidence for `.plan/mirai-reachability-poc.md` steps 1 to 4. Everything here was
run on this machine; the tables in [Results](#results) are regenerated by
`run.sh`, which fails if a case stops matching.

Nothing is written inside the repository. `run.sh` copies the two fixtures to
`/tmp/opencode/mirai-poc` and builds them there.

```sh
tools/mirai-poc/run.sh
```

## Tool under test

| Item             | Value                                                                                                                 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| Distribution     | [endorlabs/MIRAI](https://github.com/endorlabs/MIRAI), the maintained fork. `facebookexperimental/MIRAI` is archived. |
| Version          | `v1.1.12`, tag object `3309f3ff`                                                                                      |
| `main` HEAD      | `aae0a56f91d9a0a62073bb86e7b2c9793cefc24b` (2025-03-04), `ahead_by: 0` against the tag                                |
| Releases         | 3, latest `v1.1.12` on 2025-03-04, no binary assets                                                                   |
| Repository state | `archived: false`, no commit to `main` since 2025-03-04. Effectively frozen.                                          |
| Compiler         | `nightly-2025-01-10`, see below                                                                                       |
| Local install    | `~/.cargo/bin/{mirai,cargo-mirai}` `1.1.12`, built with that compiler                                                 |

The compiler requirement is read from the tool's own `rust-toolchain.toml`, which
pins `nightly-2025-01-10` (`rustc 1.86.0-nightly (824759493 2025-01-09)`) with
the `rustc-dev` and `rust-src` components. MIRAI is a `rustc` driver linked
against the compiler's private API, so it can only analyze code built by the exact
nightly it was compiled against. That nightly is already installed here, so
nothing had to be installed or pinned: the backend's own toolchain (`stable`,
`rustc 1.96.0`, edition 2024) is untouched and the fixtures are built out of tree.

`mirai` on its own fails with
`error while loading shared libraries: librustc_driver-de0738ad3f16bd9a.so`, which
is the pinned nightly's driver library. `cargo-mirai` puts the toolchain `lib`
directory on `LD_LIBRARY_PATH` before re-executing, so `cargo mirai` works.

## Running it

MIRAI is driven through `MIRAI_FLAGS` and cargo, not through annotations on the
program being analyzed:

```sh
CARGO_TARGET_DIR="$scratch" MIRAI_FLAGS="--diag=paranoid" \
  cargo +nightly-2025-01-10 mirai --lib
```

`--single_func <name>` narrows the analysis to one function. `--diag` is one of
`default`, `verify`, `library`, `paranoid`.

**Reproduction gotcha, confirmed:** MIRAI is a `rustc` wrapper. If cargo considers
the crate fresh it never invokes MIRAI, and the run reports nothing and exits 0.
Every case in `run.sh` therefore uses its own target directory. A shared target
directory yields a table of silent runs that look exactly like clean results.

## Results

### Diagnostic level decides almost everything

Whole-crate run of `fixture`, which contains a request-derived `unwrap`, an index
out of bounds and a private helper:

| `--diag`   | diagnostics |
| ---------- | ----------- |
| `default`  | 0           |
| `verify`   | 0           |
| `paranoid` | 10          |

`verify` reports only what it can prove. A function parameter is unconstrained, so
a panic reachable from one is only _possible_, and only `paranoid` reports it.
This is the main knob: the level that finds request-derived panics is the same
level that emits the noise described below.

### Panic baseline, no annotations

`fixture/`, one function per row, `--diag=paranoid`:

| Case                           | Shape                                   | Reported        |
| ------------------------------ | --------------------------------------- | --------------- |
| `case_a_request_unwrap`        | parameter to `Option::unwrap`           | yes             |
| `case_b_config_invariant`      | `Some(7)` built locally, then `unwrap`  | no, proven safe |
| `case_c_helper`                | parameter to private helper to `unwrap` | yes             |
| `case_d_move_closure`          | parameter to `move` closure to `unwrap` | yes             |
| `case_e_spawn_blocking`        | parameter to `thread::spawn` closure    | **no**          |
| `case_f_index_out_of_bounds`   | parameter to slice index                | yes             |
| `case_g_explicit_panic`        | `panic!` on a request-derived condition | **no**          |
| `case_h_request_expect`        | parameter to `Option::expect`           | **no**          |
| `case_i_request_result_unwrap` | parameter to `Result::unwrap`           | yes             |

Reported messages, verbatim:

- `possible called \`Option::unwrap()\` on a \`None\` value`for`case_a`,
`case_c`and`case_d`
- `possible index out of bounds` for `case_f`
- `possible result unwrap failed` for `case_i`

So a helper and a `move` closure are traversed, which is the part of the plan's
step 4 that works. The locally constructed `Some(7)` in `case_b` is the
false-positive control and stays silent.

Two silent rows are modelling choices rather than limits of this configuration:

- `Option::expect` is mapped to `Option::expect_failed`, whose body in
  `standard_contracts/src/foreign_contracts.rs` is `assume_unreachable!()` with
  the comment "We currently treat expect as an explicit assumption made by the
  programmer". `expect` is unreachable by construction. This matters because plan
  step 5 is written around `expect`.
- A written `panic!` is never a diagnostic. The contract is
  `default_contract!(panic_nounwind_fmt)`, and `default_contract!` expands to
  `result!()`, an unconstrained return rather than a report. MIRAI does visit the
  call: `MIRAI_LOG=debug` shows
  `_2 = std::rt::panic_fmt(move _3) -> unwind continue` inside
  `case_g_explicit_panic`, and then reports nothing. The panics MIRAI does report
  come from its own abstract models of library operations, which is why the
  upstream `panic_fmt.rs` test reports a slice-bounds message rather than a panic
  message.

The source readings in this section are from the v1.1.12 checkout. The behavioral
half of each claim is what `run.sh` checks.

### First unsupported shape

`case_e_spawn_blocking`: the value moved into a `thread::spawn` closure is never
analyzed. The run reports `possible result unwrap failed` for the outer
`.join().unwrap()` and then noise from inside the standard library, but nothing
about the `unwrap()` inside the spawned closure:

```
possible called `Option::unwrap()` on a `None` value   <- absent
incomplete analysis of call because of a nested call to a function without a MIR body
  --> src/lib.rs:42:5
  --> .../library/std/src/thread/mod.rs:469:32
possible dummy argument{}
the called function did not resolve to an implementation with a MIR body
The union is not fully initialized by this assignment
```

This is the shape of the backend's `spawn_blocking` calls. **Inferred, not
confirmed against the backend:** the fixture uses `std::thread::spawn` because
`tokio` is not in the isolated fixture. The reported mechanism is a
`nested call to a function without a MIR body`, which belongs to the
`thread::spawn` call rather than to tokio, but a tokio-specific run is needed
before claiming it for `spawn_blocking`.

### Only the root crate's own bodies are analyzed

`cargo-mirai` calls `mirai` only for the crate named by `MIRAI_CRATE`
(`checker/src/cargo_mirai.rs`) and compiles dependencies with plain `rustc`.
Confirmed with a two-crate fixture:

- a dependency function panics and the root calls it: reported, with the span at
  the root call site and a "related location" pointing into the dependency
- a dependency function panics and the root never calls it: not reported at all

So a panic inside `utils/snapfab` or a third-party crate is only surfaced if a
root-crate body reaches it. Panics in unreached dependency code are invisible.

### Diagnostics never fail the build

Every MIRAI diagnostic is emitted as a `struct_span_warn`, so the exit code is 0
in all 23 cases, including the ones with findings. Neither
`RUSTFLAGS="-D warnings"` nor `-D warnings` in `MIRAI_FLAGS` promotes them: the
diagnostics carry no lint level for rustc to gate on. Putting both in `MIRAI_FLAGS`
is not usable at all, because rustc then rejects the MIRAI-only `--diag` flag
with `error: Unrecognized option: 'diag'`.

MIRAI has one exit-code mechanism, the `//~ expected error` harness in
`checker/src/expected_errors.rs`. **Confirmed unreachable from `cargo mirai`:** it
is gated on `MiraiCallbacks::test_run`, which only
`callbacks::MiraiCallbacks::test_runner` sets, and that is used exclusively by
MIRAI's own `checker/tests/integration_tests.rs`. A fixture with a `tests/gate.rs`
integration target and `//~` comments is analyzed correctly by `cargo mirai`: MIRAI
does select and analyze the `#[test]` function, and the `//~` comments are
silently ignored, exit 0. The in-source `// MIRAI_FLAGS` comment is read by the
same harness and is ignored by `cargo mirai` as well.

**A gate would have to scrape `[MIRAI]` out of the output.** It would also have to
cope with the std-internal noise that `--diag=paranoid` produces: a whole-crate run
also reports spans inside `core/src/sync/atomic.rs`, `std/src/ffi/os_str.rs` and
`std/src/thread/mod.rs`.

### Source/sink modeling with annotations

`fixture-taint/`, all at `--diag=verify`. MIRAI 1.1.12 has no built-in untrusted
notion. The only taint mechanism is its tag domain, where `add_tag!` is the source
and `precondition!(does_not_have_tag!(..))` is the sink-side check. The
annotation crate is `mirai-annotations 1.12.0` from crates.io: dependency-free,
edition 2021, compiles under the pinned nightly.

| Case                                  | Where the tag is placed           | Sink precondition     |
| ------------------------------------- | --------------------------------- | --------------------- |
| `t3_untagged_control`                 | never tagged                      | not reported, correct |
| `t5_tagged_field`                     | struct field                      | **reported**          |
| `t11_tag_param_pass_by_value`         | handler parameter                 | **reported**          |
| `t1_tagged_into_helper`               | local `let` copy                  | not reported          |
| `t2_tagged_into_closure`              | local `let` copy                  | not reported          |
| `t4_sanitizer_is_a_no_op`             | local `let` copy                  | not reported          |
| `t7_tagged_local_direct_sink`         | local `let` copy                  | not reported          |
| `t8_intervening_ref_call`             | local `let` copy                  | not reported          |
| `t9_inline_sink`                      | local `let` copy                  | not reported          |
| `t6_taint_does_not_survive_rebinding` | local `let` copy, value discarded | not reported, correct |

Answering the two questions the experiment was meant to settle:

1. **Yes, request-derived input must be explicitly tagged.** MIRAI has no
   implicit untrusted marking, and an untagged value never trips the sink
   (`t3`). Every request field that should count as untrusted needs an explicit
   `add_tag!` at the boundary.
2. **The tag does not survive being placed on a local binding.** `t5` and `t11`
   fire, and they are the two cases that tag a _place_ the sink can still name: a
   struct field, or the function parameter itself. Every case that first copies
   the request value into a `let` is silent, including `t9`, where the source and
   the sink are in the same function, so the call boundary is not the cause.
   `t10` reports `possible false verification condition` for
   `verify!(has_tag!(&id, ..))` on the same local, which fits the tag never being
   established there rather than a check being skipped.

`run.sh` checks all of these, so the distinction is evidence and not a reading of
the source.

Not tested: whether a tag can be removed once added. `t4` was meant to cover that,
but it is silent for the unrelated reason above, so sanitization is still open.
MIRAI's own doc comment for `add_tag!` states "Once added, a tag cannot be
removed", which makes it unlikely to be expressible, but that is a claim from a doc
comment and not a measurement.

## What this means for the backend

Not implemented, listed so the parent agent can weigh the integration decision in
plan step 6.

- Against the current `syn` registry, MIRAI at `--diag=paranoid` is strictly
  stronger on the shapes in `fixture`: it connects a request-derived value to an
  `unwrap` through a helper and a `move` closure, which a source-level "handler
  contains `unwrap`" registry cannot do.
- The cost is the gate mechanism. Nothing fails the build, so a wrapper has to
  scrape output, and `--diag=paranoid` also emits diagnostics inside `core` and
  `std` that have to be filtered out.
- `spawn_blocking` is not covered, and that is where `get_rows` and
  `get_scroll_bar` do their work.
- The taint mechanism needs `mirai-annotations` in the backend and `add_tag!` plus
  `precondition!` at every request boundary and every sink. That is MIRAI-only
  code in the shipped crate, which plan step 3 and this task's constraints rule
  out as a first move. The tag results argue against it too: the shape that works
  is tagging a parameter or a struct field, which does not map onto Rocket's
  generated request structs without annotating generated code.
