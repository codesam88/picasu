# MIRAI reachability PoC

Evidence for `.plan/mirai-reachability-poc.md` steps 1 to 5. Everything here was
run on this machine; the tables are regenerated by `run.sh`, `run-shapes.sh` and
`run-backend.sh`, which fail if a case stops matching. Steps 1 to 4 are under
[Results](#results), step 5 and the decision under
[Step 5](#step-5-the-real-backend-and-the-real-bodies).

Nothing is written inside the repository. All three scripts copy what they need
to `/tmp/opencode/mirai-poc` and build it there.

```sh
tools/mirai-poc/run.sh          # panic baseline, taint modelling (no dependencies)
tools/mirai-poc/run-shapes.sh   # Rocket/tokio handler shapes and the real backend
                                # bodies (has dependencies)
tools/mirai-poc/run-backend.sh  # the three runs that are expected to fail
```

## Tool under test

| Item             | Value                                                                                                                 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| Distribution     | [endorlabs/MIRAI](https://github.com/endorlabs/MIRAI), the maintained fork. `facebookexperimental/MIRAI` is archived. |
| Version          | `v1.1.12`, tag object `3309f3ff`                                                                                      |
| `main` HEAD      | `aae0a56f91d9a0a62073bb86e7b2c9793cefc24b` (2025-03-04), `ahead_by: 0` against the tag                                |
| Releases         | 3, latest `v1.1.12` on 2025-03-04, no binary assets                                                                   |
| Repository state | `archived: false`, no commit to `main` since 2025-03-04. Effectively frozen.                                          |
| Compiler         | `nightly-2025-01-10`, see below                                                                                       |
| Local install    | `~/.cargo/bin/{mirai,cargo-mirai}` `1.1.12`, built with that compiler                                                 |

The compiler requirement is read from the tool's own `rust-toolchain.toml`, which
pins `nightly-2025-01-10` (`rustc 1.86.0-nightly (824759493 2025-01-09)`) with
the `rustc-dev` and `rust-src` components. MIRAI is a `rustc` driver linked
against the compiler's private API, so it can only analyze code built by the exact
nightly it was compiled against. That nightly is already installed here, so
nothing had to be installed or pinned: the backend's own toolchain (`stable`,
`rustc 1.96.0`, edition 2024) is untouched and the fixtures are built out of tree.

`mirai` on its own fails with
`error while loading shared libraries: librustc_driver-de0738ad3f16bd9a.so`, which
is the pinned nightly's driver library. `cargo-mirai` puts the toolchain `lib`
directory on `LD_LIBRARY_PATH` before re-executing, so `cargo mirai` works.

## Running it

MIRAI is driven through `MIRAI_FLAGS` and cargo, not through annotations on the
program being analyzed:

```sh
CARGO_TARGET_DIR="$scratch" MIRAI_FLAGS="--diag=paranoid" \
  cargo +nightly-2025-01-10 mirai --lib
```

`--single_func <name>` narrows the analysis to one function. `--diag` is one of
`default`, `verify`, `library`, `paranoid`.

**Reproduction gotcha, confirmed:** MIRAI is a `rustc` wrapper. If cargo considers
the crate fresh it never invokes MIRAI, and the run reports nothing and exits 0.
Every case in `run.sh` therefore uses its own target directory. A shared target
directory yields a table of silent runs that look exactly like clean results.

## Results

### Diagnostic level decides almost everything

Whole-crate run of `fixture`, which contains a request-derived `unwrap`, an index
out of bounds and a private helper:

| `--diag`   | diagnostics |
| ---------- | ----------- |
| `default`  | 0           |
| `verify`   | 0           |
| `paranoid` | 10          |

`verify` reports only what it can prove. A function parameter is unconstrained, so
a panic reachable from one is only _possible_, and only `paranoid` reports it.
This is the main knob: the level that finds request-derived panics is the same
level that emits the noise described below.

Two silent rows are modelling choices rather than limits of this configuration:

- `Option::expect` is mapped to `Option::expect_failed`, whose body in
  `standard_contracts/src/foreign_contracts.rs` is `assume_unreachable!()` with
  the comment "We currently treat expect as an explicit assumption made by the
  programmer". `expect` is unreachable by construction. This matters because plan
  step 5 is written around `expect`. The qualifier is `Option`: there is no
  `result::expect_failed` contract, so `Result::expect` *is* reported
  (`h21_query_primitive_to_result_expect` and `r3_get_guard_propagated_expect`
  below), which is the form `TreeSnapshot::read_scrollbar(..).expect(..)` takes.
- A written `panic!` is never a diagnostic. The contract is
  `default_contract!(panic_nounwind_fmt)`, and `default_contract!` expands to
  `result!()`, an unconstrained return rather than a report. MIRAI does visit the
  call: `MIRAI_LOG=debug` shows
  `_2 = std::rt::panic_fmt(move _3) -> unwind continue` inside
  `case_g_explicit_panic`, and then reports nothing. The panics MIRAI does report
  come from its own abstract models of library operations, which is why the
  upstream `panic_fmt.rs` test reports a slice-bounds message rather than a panic
  message.

The source readings in this section are from the v1.1.12 checkout. The behavioral
half of each claim is what `run.sh` checks.

### First unsupported shape

`case_e_spawn_blocking`: the value moved into a `thread::spawn` closure is never
analyzed. The run reports `possible result unwrap failed` for the outer
`.join().unwrap()` and then noise from inside the standard library, but nothing
about the `unwrap()` inside the spawned closure:

```

incomplete analysis of call because of a nested call to a function without a MIR body
  --> src/lib.rs:42:5
  --> .../library/std/src/thread/mod.rs:469:32

the called function did not resolve to an implementation with a MIR body

```

This is the shape of the backend's `spawn_blocking` calls. **Now confirmed, not
inferred:** the later tokio run in [Rocket and tokio handler
shapes](#rocket-and-tokio-handler-shapes) reproduces the same outcome with the real
`tokio::task::spawn_blocking`, and locates the dead end exactly. The report
mechanism is the same `nested call to a function without a MIR body`, and in both
cases the missing call is the one that would start the thread.

### Only the root crate's own bodies are analyzed

`cargo-mirai` installs itself as `RUSTC_WRAPPER` and sets
`RUSTFLAGS="--cfg mirai -Z always_encode_mir"` for the whole graph, but only
*analyzes* the crate named by `MIRAI_CRATE` with a matching crate type
(`checker/src/cargo_mirai.rs:187`); every other crate is handed back to plain
`rustc`. Because of `-Z always_encode_mir`, dependency MIR is still in the
metadata, so calls from the analyzed crate into a dependency *are* followed.
Confirmed with a two-crate fixture:

- a dependency function panics and the root calls it: reported, with the span at
  the root call site and a "related location" pointing into the dependency
- a dependency function panics and the root never calls it: not reported at all

and confirmed again with tokio in the graph, where a single `spawn_blocking` call
pulls MIRAI through 228 bodies and produces 12 diagnostics whose spans are inside
`tokio-1.53.1/src/...`, none of them in the analyzed crate. So a panic inside
`utils/snapfab` or a third-party crate is surfaced if and only if a root-crate body
reaches it, and the reported span can be in the dependency rather than in the
crate a gate would be filtering for.

### Diagnostics never fail the build

Every MIRAI diagnostic is emitted as a `struct_span_warn`, so the exit code is 0
in all 23 cases, including the ones with findings. Neither
`RUSTFLAGS="-D warnings"` nor `-D warnings` in `MIRAI_FLAGS` promotes them: the
diagnostics carry no lint level for rustc to gate on. Putting both in `MIRAI_FLAGS`
is not usable at all, because rustc then rejects the MIRAI-only `--diag` flag
with `error: Unrecognized option: 'diag'`.

MIRAI has one exit-code mechanism, the `//~ expected error` harness in
`checker/src/expected_errors.rs`. **Confirmed unreachable from `cargo mirai`:** it
is gated on `MiraiCallbacks::test_run`, which only
`callbacks::MiraiCallbacks::test_runner` sets, and that is used exclusively by
MIRAI's own `checker/tests/integration_tests.rs`. A fixture with a `tests/gate.rs`
integration target and `//~` comments is analyzed correctly by `cargo mirai`: MIRAI
does select and analyze the `#[test]` function, and the `//~` comments are
silently ignored, exit 0. The in-source `// MIRAI_FLAGS` comment is read by the
same harness and is ignored by `cargo mirai` as well.

**A gate would have to scrape `[MIRAI]` out of the output.** It would also have to
cope with the std-internal noise that `--diag=paranoid` produces: a whole-crate run
also reports spans inside `core/src/sync/atomic.rs`, `std/src/ffi/os_str.rs` and
`std/src/thread/mod.rs`. With a real dependency in the graph the spans are not
confined to `core`/`std` either, see
[below](#rocket-and-tokio-handler-shapes). `run-shapes.sh` asserts the exit code
and the diagnostic count as separate columns for all 62 analysis rows rather than
relying on either one alone.

### Source/sink modeling with annotations

`fixture-taint/`, all at `--diag=verify`. MIRAI 1.1.12 has no built-in untrusted
notion. The only taint mechanism is its tag domain, where `add_tag!` is the source
and `precondition!(does_not_have_tag!(..))` is the sink-side check. The
annotation crate is `mirai-annotations 1.12.0` from crates.io: dependency-free,
edition 2021, compiles under the pinned nightly.

| Case                                  | Where the tag is placed           | Sink precondition     |
| ------------------------------------- | --------------------------------- | --------------------- |
| `t3_untagged_control`                 | never tagged                      | not reported, correct |
| `t5_tagged_field`                     | struct field                      | **reported**          |
| `t11_tag_param_pass_by_value`         | handler parameter                 | **reported**          |
| `t1_tagged_into_helper`               | local `let` copy                  | not reported          |
| `t2_tagged_into_closure`              | local `let` copy                  | not reported          |
| `t4_sanitizer_is_a_no_op`             | local `let` copy                  | not reported          |
| `t7_tagged_local_direct_sink`         | local `let` copy                  | not reported          |
| `t8_intervening_ref_call`             | local `let` copy                  | not reported          |
| `t9_inline_sink`                      | local `let` copy                  | not reported          |
| `t6_taint_does_not_survive_rebinding` | local `let` copy, value discarded | not reported, correct |

Answering the two questions the experiment was meant to settle:

1. **Yes, request-derived input must be explicitly tagged.** MIRAI has no
   implicit untrusted marking, and an untagged value never trips the sink
   (`t3`). Every request field that should count as untrusted needs an explicit
   `add_tag!` at the boundary.
2. **The tag does not survive being placed on a local binding.** `t5` and `t11`
   fire, and they are the two cases that tag a _place_ the sink can still name: a
   struct field, or the function parameter itself. Every case that first copies
   the request value into a `let` is silent, including `t9`, where the source and
   the sink are in the same function, so the call boundary is not the cause.
   `t10` reports `possible false verification condition` for
   `verify!(has_tag!(&id, ..))` on the same local, which fits the tag never being
   established there rather than a check being skipped.

`run.sh` checks all of these, so the distinction is evidence and not a reading of
the source.

Not tested: whether a tag can be removed once added. `t4` was meant to cover that,
but it is silent for the unrelated reason above, so sanitization is still open.
MIRAI's own doc comment for `add_tag!` states "Once added, a tag cannot be
removed", which makes it unlikely to be expressible, but that is a claim from a doc
comment and not a measurement.

### Rocket and tokio handler shapes

The second pass over step 4. `run-shapes.sh` runs five fixtures:
`fixture-handler` (dependency-free stand-ins for the handler shapes),
`fixture-tokio` (the real `tokio::task::spawn_blocking`), `fixture-rocket` (the
real `#[get]`/`#[post]` attribute and Rocket's `Json<T>`), `fixture-backend` (the
real `get_rows`/`get_scroll_bar`/`read_scrollbar`/`read_row` bodies from step 5)
and `fixture-msrv` (the first blocker, isolated). 90 rows: 88 analysis cases and
2 blocker checks, all passing. MIRAI's exit code is 0 on all 88 analysis cases,
46 of which have diagnostics in the fixture.

The runner reports four things per row instead of only a diagnostic count, because
the two are independent: `EXIT` (asserted to be 0, since MIRAI never fails the
build), `SRC` (diagnostics whose span is in the fixture), `ALL` (including the
standard-library and dependency noise) and `LIVE`, which asserts that MIRAI
actually re-analyzed the selected function. `LIVE` is not cosmetic: MIRAI is a
`rustc` wrapper, so a fresh cargo fingerprint produces a silent, successful,
completely empty run.

#### First blocker: the dependency MSRV, not MIRAI

rocket 0.5.1 has a non-optional dependency on `time`, and pulls in
`encoding_rs` through `rocket_http`. Their current versions declare
`rust-version = 1.88`; MIRAI's pinned compiler is `rustc 1.86.0-nightly`. Cargo
refuses to build the graph:

```
error: rustc 1.86.0-nightly is not supported by the following packages:
  encoding_rs@0.8.42 requires rustc 1.88
  time@0.3.55 requires rustc 1.88.0
  time-core@0.1.9 requires rustc 1.88.0
  time-macros@0.2.32 requires rustc 1.88.0
```

Two things about that failure are easy to get wrong. `cargo generate-lockfile`
does **not** fail: it only annotates the resolution (`Adding time v0.3.55
(requires Rust 1.88.0)`) and exits 0, so a lock-file step that only checks the exit
code reports success on a graph that cannot be built. The hard error comes from
compiling.

And the root `Cargo.lock` of this repository pins `time 0.3.55`, `time-core
0.1.9`, `time-macros 0.2.32` and `encoding_rs 0.8.40`, so **the backend's own
resolved dependency set cannot be compiled by MIRAI's pinned compiler**. Any
backend experiment has to pin these back first: `time 0.3.45`, `time-core 0.1.7`,
`time-macros 0.2.25`, `encoding_rs 0.8.35`, the newest releases whose declared MSRV
the pinned nightly accepts. `run-shapes.sh` applies those pins to the scratch copy.

The same check over the whole root lock is worse than the rocket case suggests.
Reading the `rust-version` field of every registry package in the root `Cargo.lock`
out of the local crates.io index cache: **18 of 480 packages require rustc newer
than 1.86**, and they include `redb 4.3.0` (1.90), `image 0.25.10` (1.88),
`jsonwebtoken 11.1.0` (1.88) and the whole `icu_*` stack (1.88). 141 packages have
no `rust-version` in the index, so 18 is a lower bound. This is metadata, not a
build: a `cargo build` of the backend on the pinned nightly would fail on the first
of them, and `redb` in particular is a major-version downgrade rather than a
patch-level pin. Pinning the backend's graph down to `nightly-2025-01-10` is
therefore a real piece of work, and a cheaper route to a backend experiment is a
nearer crate that does not pull `redb`, `image` or `jsonwebtoken`.

**Correction, from the step 5 build:** the `icu_*` packages are in the lock but
**not in the lib target's graph** — `cargo tree -p picasu --edges normal` contains
no `icu_*` entry and `cargo tree -i icu_provider` prints nothing, so they are
reached only by another target or another platform. The 18 is a figure for the
lock; the figure for the crate MIRAI would analyze is below.

`fixture-msrv` is the reduction of this blocker: two dependencies, one empty
function, no rocket and no route. `cargo check --lib` on it exits 101 with the
message above, and exits 0 with the pins. Both are gated rows in the matrix.

A second, environmental blocker, not a MIRAI property: rustc and MIRAI's summary
store both write temporary files under the system temp directory. This machine has
a per-user quota on `/tmp` that `df` does not report, and hitting it surfaces as
`Disk quota exceeded` from rustc, or, for MIRAI, as an internal panic in
`SummaryCache::create_summary_store_if_needed` with exit 101. `run-shapes.sh`
therefore points `TMPDIR` at its scratch directory.

Messages, verbatim:

Four answers, one case each:

1. **A query/path primitive is treated as unconstrained input.** `h1` reports
   ``possible called `Option::unwrap()` on a `None` value`` at the handler's call
   site with the helper as a related location. `--diag=verify` reports nothing,
   because a parameter is unconstrained and a possible panic is not a proof; the
   whole crate at `verify` has 3 diagnostics, all of them certain panics. The same
   holds for the `TREE_SNAPSHOT.read_row(..)` singleton-method form (`h4`), for
   arithmetic (`h5`), and for Rocket's real query parameter in `r1` below.
2. **`spawn_blocking` is a dead end, and so is `thread::spawn`.** See below.
3. **A body works.** Both access paths are reported, with the stand-in
   (`h6`-`h9`) and with Rocket's real `Json<T>` under a real `#[post]`
   (`r4`/`r5`).
4. **A discarded guard is invisible.** `h10`/`h11` and `h19`/`h20` are identical
   in every column, at both levels. MIRAI has no notion of a request guard, so
   `let _ = auth;` is ordinary unused code. It does not even cost a diagnostic:
   `h12` and `h13` are both 0, and unlike `spawn_blocking` the `?` neither
   produces an `incomplete analysis` warning nor suppresses the sink behind it
   (`h20` still reports a certain panic at `verify`, where `h16` reports nothing).
   So the phase-5 question "is the timestamp guard propagated" is not a question
   MIRAI can answer at any diagnostic level.

`Result::expect` versus `Option::expect` is worth separating, because step 5 is
written around `expect`. The contract for `option::expect_failed` in
`standard_contracts/src/foreign_contracts.rs:4321` is `assume_unreachable!()`
("We currently treat expect as an explicit assumption made by the
programmer"), and there is no `result::expect_failed` contract at all, so
`Result::expect` falls back to `result::unwrap_failed`, which is a panic. Hence
`h2` is silent and `h21` is reported, and the earlier note in this file that
MIRAI "cannot see `expect`" holds only for `Option::expect`. Since
`TreeSnapshot::read_scrollbar` returns a `Result`, its `.expect(..)` is visible.

#### The hand-off, and where exactly it stops

`fixture-tokio`, `--diag=paranoid`:

| Case                                    | Shape                                    | `SRC` | `ALL` | time  |
| --------------------------------------- | ---------------------------------------- | ----- | ----- | ----- |
| `k1_spawn_blocking_closure_unwrap`      | `unwrap` inside the closure              | 0     | 23    | 15 s  |
| `k2_spawn_blocking_closure_expect`      | `expect` inside the closure              | 0     | 23    | 16 s  |
| `k3_spawn_blocking_closure_index`       | index inside the closure                 | 0     | 23    | 15 s  |
| `k4_spawn_blocking_closure_calls_helper`| sink in a helper the closure calls       | 0     | 23    | 13 s  |
| `k5_sync_closure_called_directly`       | the same closure, called in the fn       | 1     | 1     | 0.3 s |
| `k6_sync_helper_sink`                   | a private helper, tokio in the graph     | 1     | 1     | 0.3 s |
| `k7_async_await_handle_unwrap`          | `async` fn unwrapping the `JoinHandle`   | 0     | 0     | 0.3 s |
| `k8_async_get_rows_shape`               | the whole `get_rows` shape               | 0     | 0     | 0.3 s |

MIRAI does not merely give up at the `spawn_blocking` call. With
`MIRAI_LOG=debug` it enters **228 distinct bodies** on the way: the handler, then
`tokio::task::blocking::spawn_blocking`, `runtime::blocking::pool::spawn_blocking`,
`runtime::task::capture`, `blocking::pool::spawn_blocking_inner`,
`blocking::pool::spawn_thread`, `std::thread::Builder::new`, and so on through
hashbrown and `core_arch`. The closure is carried the whole way as
`param_1.func: DefId(0:13 ~ ...::k1_spawn_blocking_closure_unwrap::{closure#0})` and
is never called. The dead end is exact and local:

```
warning: [MIRAI] the called function did not resolve to an implementation with a MIR body
  --> tokio-1.53.1/src/runtime/blocking/pool.rs:463:55
   |
463|         let mut builder = thread::Builder::new().name((self.inner.thread_name)());
```

`spawn_thread` is the function that would create the worker thread on which the
closure eventually runs, and `std::thread::Builder::new` has neither a MIR body
MIRAI can resolve nor a foreign contract, so the worker thread is never created in
the abstract model. The closure is therefore unreachable, and the phase-1
`thread::spawn` result is the same wall one level deeper: MIRAI never follows a
closure into a thread.

`h14`/`h15` are the discriminating pair. The same `FnOnce` hand-off, defined in the
analyzed crate instead of in a dependency, **is** followed and the sink **is**
reported. So the limitation is not closures, not `move`, and not the generic
hand-off; it is that the thread handoff in both `std` and tokio ends in a call
MIRAI cannot resolve.

The 23 `ALL` diagnostics of a `spawn_blocking` call are noise, and 12 of them have
spans inside tokio's own source, including one false positive in tokio
(`possible attempt to add with overflow` at
`runtime/blocking/pool.rs:450`). A gate cannot filter on "our crate" alone.

#### Rocket, for real

`fixture-rocket` on rocket 0.5.1 with the pinned `time`/`encoding_rs`. The
`#[get]`/`#[post]` attribute is not a blocker: the macro keeps the handler `pub`,
the route type-checks, and MIRAI analyzes it.

| Case                                  | Shape                                              | `verify` | `paranoid` |
| ------------------------------------- | -------------------------------------------------- | -------- | ---------- |
| `r1_get_primitive_to_helper_unwrap`   | `#[get]`, `i64` query primitive, `unwrap`           | 0        | 1          |

| `r6_get_async_spawn_blocking_helper`  | `get_rows`: `#[get] async`, guard `?`, `spawn_blocking` | 0    | 0          |
| `r7_get_async_spawn_blocking_closure` | `#[get] async`, `spawn_blocking` closure with a sink | 0        | 0          |
| whole crate                           | all 7 routes at once                                | -        | 12         |

The whole-crate count of 12 is 5 sinks plus one
`incomplete analysis of call because of a nested call to a function without a MIR
body` **per route**, reported at the `#[get(..)]`/`#[post(..)]` attribute line
itself, i.e. inside the macro-generated `into_route` function. A crate-wide run
therefore pays one incomplete-analysis diagnostic per registered route, and it
analyzes 21 entry points: the 7 handlers, the 7 generated `into_route` methods,
`GuardTimestamp::from_request`, the two `TreeSnapshot` methods, the serde-generated
`fmt`/`deserialize`/`expecting` methods, and `TREE_SNAPSHOT` itself.

`r6` and `r7` are the important negatives: with the real attribute, the real guard
and the real `spawn_blocking`, MIRAI reports nothing, because both handlers are
`async`.

#### `async` is the largest gap, and it is not a modelling detail

`h24` is the reduction: an `async fn` whose body provably panics on a locally
constructed `None`. It is silent at `verify` and at `paranoid`. The same panic in
a plain function is reported as certain (`h23`). An `async fn` body is a coroutine
body, and a coroutine body is only entered by polling a future, which MIRAI never
does. An `async` block inside a synchronous function is the same
(`h18`), as is the `JoinHandle` unwrap in an `async` handler (`k7`).

MIRAI *selects* these functions: the `LIVE` column is asserted from
`MIRAI_LOG=info`, which prints `analyzing selected function
mirai_poc_fixture_handler.h24_async_concrete_sink` for the `h24` row, and the
whole-crate run logs the same line without `selected` for every `pub` function in
the fixture. The body is entered and nothing in it is evaluated. Closures behave
the same way, with one exception: `h22` (an uncalled closure with a certain panic)
is silent while `h23` (the same closure, called) is reported, so an uncalled
closure is not analyzed as an entry point and a called one is analyzed inline.

This is what phase 1 already showed for `Option::expect` and closures, but its
scope is much larger than the plan assumed: `get_rows` is `pub async fn`, and so
is every handler in `backend/src/router/{get,put,post}`. Of the 64 route attributes
in the backend, the async ones are invisible to MIRAI at any diagnostic level, and
so is every body they delegate to through `.await`.

#### Cost

Per case, from one full run on this machine. The rows that build dependencies
vary by tens of percent between runs; the per-handler rows are stable.

| Fixture                 | cases | min    | median | max      |
| ----------------------- | ----- | ------ | ------ | -------- |
| `fixture-handler`       | 38    | 331 ms | 387 ms | 900 ms   |
| `fixture-backend`       | 26    | 305 ms | 677 ms | 1.4 s    |
| `fixture-tokio`         | 13    | 274 ms | 5.5 s  | 16.2 s   |
| `fixture-rocket`        | 11    | 591 ms | 794 ms | 38.8 s   |

The `fixture-tokio` median is bimodal, and the split is the finding rather than
noise: a case that calls `spawn_blocking` costs 13-16 s of analysis and reports
nothing, and every other case costs 0.3 s. The 38.8 s `fixture-rocket` row is the
crate-wide case, which also builds the 163-package rocket dependency tree through
the MIRAI driver. That build is 391 MB of target directory, and `cargo-mirai`
sets `RUSTFLAGS="--cfg mirai -Z always_encode_mir"` for every crate in the graph
(`checker/src/cargo_mirai.rs:155`), which is what makes it that large.

Extrapolating to the backend is guesswork, but the pieces are measured: 483
packages in the root lock instead of 163, 20.9k lines of Rust across 107 files
instead of 165, and 64 routes. A single whole-crate `cargo mirai --lib` on the
backend would have to build that graph with `-Z always_encode_mir` and then analyze
every public non-generic, non-const, non-higher-order body in it, with MIRAI's own
`--crate_analysis_timeout` default of 240 s. Whether that fits in a nightly lane
is unknown until it is tried; the dependency build alone is the part that is
predictable, and a crate-wide run is a single invocation, whereas per-handler
`--single_func` runs (the only way to attribute diagnostics and the only way to
reach `async`... which is impossible anyway) would re-analyze the crate per
handler. The step 5 attempt settles the question before the cost matters: the run
never reaches MIRAI, so the 240 s budget is never spent and the graph is never
built.

## Step 5: the real backend, and the real bodies

`run-backend.sh` runs the three things that are expected to fail. The first is the
command a gate would use, on a copy of the workspace so the repository's
`Cargo.lock` is never touched:

CARGO_TARGET_DIR=<scratch>/backend-target TMPDIR=<scratch> MIRAI_FLAGS=--diag=paranoid \

further down: `cookie_store 0.22.1` requires `time ^0.3.47`, and the newest `time`

two pins that are accepted, `cargo check --lib` still exits 101 with the same
error, still naming `redb` and `jsonwebtoken`.

`redb` is the hard one: **every release from 3.0.0 on declares `rust-version`
1.89 or 1.90**, so the newest acceptable is the 2.6.3 line. The backend uses
`redb::Value` as a trait bound, `ReadableTableMetadata`, `TableHandle`,
`Database::create` and `redb::Table<'_, &str, &str>`, and 2.x to 4.x is not a
patch-level move. Reaching MIRAI's compiler is a dependency-downgrade project
with production-code changes, not a lock-file edit.

### The reduction, and what it loses

`fixture-backend` holds the actual bodies of `get_rows`, `get_scroll_bar`,
`read_scrollbar`, `read_row`, `read_tree_snapshot` and `get_width_height`, in the
revision that still contained the panic sites (`5083c5fb^`) and in the current
one, in a crate with no dependencies. What is lost, in full:

- **Rocket.** No `#[get]`, no query-primitive parsing, no `Json<T>` plumbing;
  `../fixture-rocket` covers the attribute. A handler parameter is the trust
  boundary in either case, and the two revisions are otherwise identical.
- **The stores.** `TREE_SNAPSHOT` holds two const arrays instead of a `DashMap`
  and a redb table, and `read_tree_snapshot` returns one snapshot instead of a
  `MyCow` enum with two arms. No redb transaction, no table open, no
  `TableError`, no `LazyLock`.
- **The snapshot size.** `read_row` and `get_width_height` take the row count as a
  `usize` parameter, standing in for `MyCow::len()`. With a const length MIRAI
  proves every bounds check in `read_row` and the cases would pass for the wrong
  reason. This is the only signature change.
- **The runtime.** `spawn_blocking` is an in-crate `FnOnce` that calls its
  argument and awaiting the handle is a ready future, so a sink reported through
  the hand-off says nothing about tokio. `../fixture-tokio` has the real one.
- **chrono.** `Utc.timestamp_millis_opt(..).single()` becomes a two-field struct
  that yields `None` outside a small range, derived with operations that cannot
  overflow so that a diagnostic in a scroll-bar case is attributable to the shape
  and not to the stand-in.
- **`info!`, `Instant::now()`, `#[utoipa::path]`, `or_raise`'s closure body, the
  `Debug` derive.** No control flow. `or_raise` itself is kept, because the `?`
  it wraps is a call MIRAI may fail to resolve.

So the backend was **not** analyzed. The reduction was, and it answers the two
questions step 5 asks at the real source rather than at a list of shapes.

| `b17_snapshot_err_without_loop`         | the store lookup without a loop                    | 1          | 0        |
| `b18_snapshot_err_with_loop`            | the same lookup as a `for` loop                    | 0          | 0        |
| whole crate                             | all 18 cases at once, 31 entry points              | 22         | 0        |

† `possible attempt to add with overflow` — see below, it is MIRAI's model of
`Enumerate::next`, not a finding about the backend.
‡ `result unwrap failed`.
§ `possible attempt to multiply with overflow`.

**1. `timestamp -> read_scrollbar -> expect` is not detected.** `b1` is the exact
edge, with the sink in isolation: nothing at `paranoid`, nothing at `verify`. The
sink itself is not the problem — `b16` puts the same `Result::expect` on a
`Result` the function builds itself out of the same parameter and it is reported,
and `b5` puts `Result::unwrap` on the very same `read_scrollbar` call and is
reported too. What differs is the reachability of the `Err` branch of
`read_tree_snapshot`, and `b17`/`b18` locate it: the same lookup written as an
`if` is reported, the same lookup written as a `for` loop over the table is
silent. **MIRAI 1.1.12 loses a value that a loop produced**, so every helper that
finds its `Err` by scanning a table is opaque to it, which is the shape of
`read_tree_snapshot`, `read_scrollbar` and most of `backend/src/storage`.

**2. The discarded guard is invisible, as before.** `b14` and `b15` agree in every
column at both levels: `let _ = auth;` and `let _ = auth?;` are the same program to
MIRAI. The defect class behind the `get_rows`/`get_scroll_bar` guard fix is not
representable in the tool's model, so no diagnostic level and no annotation change
reaches it.

**3. `get_rows` is invisible for three independent reasons, and the ladder shows
which one is load-bearing.** The index sink is reported when nothing else is in
front of it (`b7`), the real `read_row` body reports only the arithmetic
(`b8`, `b9`), and the handler as written reports nothing at all (`b12`) — while a
*certain* panic in the same position is also silent (`b13`), which is the proof
that the coroutine body is never entered rather than merely unreached.

**4. The diagnostic stream on the real bodies is mostly MIRAI's own arithmetic
model.** `possible attempt to add with overflow` on `b2`, `b3`, `b4`, `b14` and
`b15` is the counter increment inside `Enumerate::next`, attributed by MIRAI to
the `.enumerate()` in the fixture and, in the backend, to the `.enumerate()` in
`read_scrollbar`. The primary span is in the analyzed crate and the related
location is in `core`, so **a span filter cannot remove it**: filtering on
`core`/`std` spans keeps every one of these. `possible attempt to multiply with
overflow` on `b8` to `b11` is the real `row_index * ROW_BATCH_NUMBER`, which
cannot overflow in practice because `row_index <= chunk_count` — a correct
"possible" report on an unreachable panic, and the only thing MIRAI says about
the `get_rows` path below the handler.

The crate-wide run is 22 diagnostics in the fixture, of which 16 are the two
arithmetic artifacts, over 31 entry points, in 1.4 s. Extrapolating is guesswork,
but the direction is measured: MIRAI's output on this code is dominated by its
model of the standard library.

### A crash that looks like a clean run

`fixture-internal-error` is four lines: a counted loop with an accumulator, i.e.
the shape of every `collect`, `sum` or counter loop in the backend.

```
Error: Argument (let ((a!1 (and (=> (and (bvslt #x0000000000000000 #x0000000000000001) ...
  at position 1 has sort (_ BitVec 64) it does not match declaration
  (declare-fun bvxor ((_ BitVec 128) (_ BitVec 128)) (_ BitVec 128))
```

MIRAI hands the loop's path condition to its Z3 encoding and Z3 rejects the
query. Cargo then reports the compilation as failed: **exit 101, and zero
`[MIRAI]` lines**, at every diagnostic level and for a crate-wide run as well. A
gate that scrapes `[MIRAI]` out of the output reads this as the cleanest possible
result unless it also asserts the exit code — which is the only mechanism MIRAI
offers, and the one it uses for its own diagnostics is unavailable (see
[Diagnostics never fail the build](#diagnostics-never-fail-the-build)).

## What this means for the backend

Step 5 settles the question the earlier passes left open, so this is now a
recommendation rather than a list for the parent agent to weigh. **Reject MIRAI
1.1.12 as a backend gate.** The evidence, in the order it matters:

- **It cannot build the backend.** The real command exits 101 in about 1 s, and the
  fix is not a lock-file edit: 7 of the 9 offending pins are refused by version
  requirements, four of them by `backend/Cargo.toml` itself, and `redb` would have
  to go from 4.x to 2.6.x. That is a dependency-downgrade project with
  production-code changes, undertaken to obtain a tool that then cannot see the
  code it is pointed at.
- **It cannot see the code it would be pointed at.** Every handler in
  `backend/src/router/{get,put,post}` is `async fn`, and no `async fn` body is
  analyzed (`b12`, `b13`, `h24`, `r6`, `r7`). `get_rows` additionally hands off to
  `spawn_blocking`, whose closure is never analyzed (`k1`-`k4`, at 13-16 s each).
  Step 5 adds a third blind spot: a value produced by a loop is lost, so a helper
  that finds its `Err` by scanning a table is opaque (`b17`/`b18`), which is the
  shape of `read_tree_snapshot` and most of `backend/src/storage`. The plan's
  acceptance criterion — `timestamp -> read_scrollbar -> expect` — is **not met**:
  `b1` is silent at every level, while the same sink on a locally built `Result`
  (`b16`) and the same value with `unwrap` (`b5`) are both reported.
- **The defect class it was wanted for is not representable.** A discarded guard
  and a propagated guard are the same program to MIRAI (`b14`/`b15`), so the class
  behind the `get_rows`/`get_scroll_bar` guard fix has no representation in the
  tool's model, at any diagnostic level and with any annotation.
- **The gate mechanics do not close.** Diagnostics never change the exit code, so
  a gate must scrape output; `--diag=paranoid` fills that output with the
  standard library's own arithmetic model, attributed by primary span to the
  analyzed crate, so span filtering does not remove them (16 of the 22
  crate-wide diagnostics in the step 5 fixture); and a plain counted loop makes
  MIRAI abort with a Z3 error, exit 101 and **zero** `[MIRAI]` lines, which a
  scraping gate reads as the cleanest possible result.
- **It is frozen.** `main` has had no commit since 2025-03-04, and the tool can
  only analyze code built by `nightly-2025-01-10`, which the backend's own
  dependency graph has already moved past.

What MIRAI was better at, and what is therefore worth keeping from this PoC: on
the shapes it can see it is strictly stronger than the `syn` registry — it
connects a request-derived `i64` query primitive, through a private helper, to an
`unwrap`, with Rocket's real `#[get]` attribute in the path (`r1`, `r2`), and it
sees through a body guard's `Deref` and `into_inner` (`r4`, `r5`). None of that
reaches the backend, because the backend's handlers are `async fn` and the
`spawn_blocking` shape. The recommendation is therefore to keep the `syn` ratchet
plus the targeted runtime tests as the mechanism, and to carry these two facts
into the next look at request-input reachability: **every `async fn` body is a
blind spot for MIR-based tools that analyze function bodies rather than futures,
and the same holds for a value produced by a loop.** Both are properties of the
approach, not of this configuration, so the next candidate should be judged on
whether it enters coroutine bodies and loop-produced values.

The taint mechanism stays out of scope either way: it needs
`mirai-annotations` in the shipped crate and `add_tag!` plus `precondition!` at
every request boundary and every sink, and the shape that works is tagging a
parameter or a struct field, which does not map onto Rocket's generated request
structs.
