## Problem

AI-assisted development is producing locally plausible changes that pass
focused TDD and DSL-driven end-to-end scenarios while still introducing
churn, migration artifacts, API drift, identifier confusion, spaghetti code,
and code smells. The existing tests demonstrate selected user workflows, but
they do not adequately test the complete external contract, architectural
boundaries, semantic invariants, or maintainability of the implementation.

The recent path-primary rework is a concrete example: the intended behavior
remained superficially functional, while stale API terminology, incorrect
identifier values at live call sites, a dead refresh path, and incomplete
OpenAPI coverage were only found by a separate review. Autogenerated OpenAPI
annotations also drifted because route registration, annotations, generated
paths, and public-spec filtering were separate sources of truth.

The goal is an automated quality gate that catches these classes of problem
without depending on manual code review for every change. It should evaluate
both behavior and implementation health, and make exceptions explicit when a
budget or rule must be exceeded.

## Proposed Directions

### Executable external contract

Extend `openapi-contract-hardening.md` into a recurring contract gate:

- Check in and diff a normalized generated public OpenAPI artifact.
- Compare mounted runtime routes with documented operations.
- Lint operation metadata, schemas, security, errors, and response fidelity.
- Detect breaking changes against the released API baseline.
- Generate contract smoke tests for reachability, validation, auth behavior,
  status families, and response schemas.

The OpenAPI document should become an executable description of the public
interface, not only a rendered reference document.

### Behavioral strength

- Add property-based tests for invariants such as indexing idempotence,
  content-hash serving, asset identity, duplicate handling, and deletion.
- Add stateful/model-based tests for watcher, indexing, album membership, and
  filesystem/database reconciliation sequences.
- Add metamorphic or differential tests where an exact expected output is
  expensive to specify, such as index-twice, move-and-move-back, or unrelated
  metadata changes.
- Add mutation testing, initially for high-risk backend domains and changed
  modules, to measure whether tests detect meaningful behavioral changes.

### Architecture and implementation health

- Define automated dependency-boundary rules for backend layers and frontend
  stores/components.
- Scan for forbidden legacy names, compatibility aliases, stale routes, and
  migration artifacts after renames or model changes.
- Track complexity, file size, duplication, dependency fan-in/fan-out,
  nesting, unchecked errors, broad types, and ignored tests as quality budgets.
- Fail or require an explicit exception when a change exceeds a budget.
- Generate a dependency and change-impact report so broad churn is visible to
  the quality gate rather than hidden inside a passing feature test.

### Invariant and AI-change controls

- Maintain a machine-readable registry of important invariants, such as
  `hash` meaning content hash and `assetId` meaning storage identity.
- Associate each invariant with static checks, runtime/property tests, and the
  affected subsystem.
- Require changes to identify affected contracts and invariants.
- Detect weakened assertions, deleted tests, relaxed types, broad formatting
  churn, and unapproved compatibility layers.
- Run cheap checks on every change, with mutation, stateful, fuzz, and broader
  architectural checks in nightly or release jobs.

## Scope and Sequencing

This is broader than `openapi-contract-hardening.md`; that plan covers the
first contract-specific findings and can supply the initial implementation
slice. A likely sequence is:

1. Public OpenAPI snapshot, route/spec parity, structural lint, and breaking
   diff.
2. Architecture boundaries, legacy-artifact scans, and changed-code quality
   budgets.
3. Property-based and stateful tests for identity, indexing, deletion, and
   watcher behavior.
4. Mutation testing and broader generated contract tests in scheduled jobs.
5. A repository-wide invariant registry and AI-specific change-impact gates.

The acceptance criterion is not simply higher test count. The resulting gates
must detect missing or stale API descriptions, semantic identifier mistakes,
behavioral regressions outside example scenarios, and measurable structural
degradation while keeping intentional exceptions reviewable and finite.
