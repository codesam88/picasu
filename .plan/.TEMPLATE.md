## Task Writing Rules

**No placeholders.** Every task must be concrete and actionable. Never write:

- `TBD`, `TODO`, `implement later`, `fill in details`
- `Add appropriate error handling` / `add validation` / `handle edge cases`
- `Write tests for the above` without actual test code
- `Similar to Task N` — repeat the content; tasks may be read out of order
- Steps that describe what to do without showing how (code blocks required for code steps)

**Bite-sized sub-steps.** For complex tasks, break into 2–5 minute actions:

- Write the failing test
- Run it to make sure it fails
- Implement the minimal code to make the test pass
- Run the tests and make sure they pass
- Commit

**Linked artifacts.** Consider if the change should include updates to:

- Project documentation (docs, READMEs)
- Example code, configs or templates
- Related tasks that reference this work

### Self-Review Checklist

After writing or updating the plan, verify:

1. **Spec coverage** — Every requirement in the spec has a corresponding task. List gaps.
2. **Placeholder scan** — No red-flag phrases from the "No placeholders" list above.
3. **Corner cases** — All corner cases called out and handled appropriately.
4. **Artifact coverage** — All affected docs, examples, and related artifacts are listed.

If issues are found, fix them inline before marking the plan ready.
